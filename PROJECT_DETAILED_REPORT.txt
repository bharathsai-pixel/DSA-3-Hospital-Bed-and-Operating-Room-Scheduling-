======================================================================
1. PROJECT OVERVIEW
======================================================================

This Java project provides a command-line simulation and a Spring REST application for assigning patients to hospitals, operating rooms (ORs), surgery start times, and beds. The command-line program uses the fixed sample dataset; the REST application persists hospital and scheduling state in a local H2 database. Both use the same scheduling algorithms and plain domain models.

The implementation combines:
1. Min-cost maximum flow routes patients to capable hospitals with separate ICU and General bed capacities.
2. Longest Processing Time (LPT) heuristic to distribute patients among compatible ORs.
3. Subset dynamic programming to sequence unique patients around time, OR, and surgeon constraints.
4. Hungarian assignment to allocate beds using priority, waiting time, and ICU bed type in a cost matrix.
5. KMP for patient/staff name search.
6. Randomized quicksort to order surgery duration before LPT.
7. KPI and schedule reports.

This is a classroom simulation using hard-coded data, not a live or clinically validated hospital system. The current Java pipeline enforces surgeon specialization and shifts; it does not model anesthetists, nurses, real-time monitoring, or violation reports.

4. IMPLEMENTATION WALKTHROUGH
======================================================================

4.1 Menu and state
The console Main loads fresh lists from SampleData and loops over choices: 1 hospitals, 2 patients, 3 run/reset pipeline, 4 emergency intake, 5 KPI report, 6 schedules, 7 KMP search, 8 discharge patient, 0 exit. Non-integer choices print "Invalid input"; unknown integers print "Invalid choice". Choice 3 resets patient schedule fields, surgeon assignments, OR slots, and bed reservations before recomputing. This describes the console program; the separate REST application uses the durable persistence layer documented in Section 14.

4.2 Hospital routing: min-cost maximum flow
HospitalRouter creates a source, one node per patient, separate General/ICU capacity lanes per hospital, and a sink. Source-to-patient capacity is one. Patient edges require compatible OR and qualified surgeon capability. ICU patients connect only to ICU lanes. Non-ICU patients can use General lanes or ICU lanes with an ICU-preservation penalty. Lane-to-sink capacity is the number of available beds of that type. Successive shortest augmenting paths use Bellman-Ford on the residual graph, including reverse edges with negative costs. Augmentation continues until no path remains: routed count is maximized first, then cost is minimized. A large cost penalizes not using the preferred hospital; Haversine distance from Patient coordinates breaks ties. The sample defaults patient coordinates to the service-area center; setLocation can provide per-patient coordinates.

4.3 OR load balancing: randomized quicksort and LPT
ApproxScheduler sorts patients by descending surgery duration with a random-pivot quicksort, then assigns each patient to a compatible OR with the smallest accumulated duration workload. This is LPT (Longest Processing Time first), a heuristic for difficult multiprocessor scheduling. Quicksort expected time is O(n log n), worst case O(n^2); OR scans cost approximately O(n*r), for n patients and r ORs. This balances workload but does not itself account for bed/equipment feasibility or exact timing. OR time selection subsequently checks a qualified surgeon and bed reservation. Patients unsupported by any OR receive a warning and no OR assignment.

4.4 Time slots: subset dynamic programming
The current DPScheduler sequences each patient once using a subset mask and end-time states. Each transition finds the earliest feasible time after the preceding selected case, existing OR bookings, arrival time, and qualified-surgeon availability. The score includes a base reward, priority bonus, and per-minute waiting penalty. For at most 14 patients on an OR it searches schedule orders exactly; larger lists use a fixed-candidate weighted-interval fallback.
Bed feasibility is checked during final assignment, and the DP does not globally optimize idle time or makespan across all ORs.

4.5 Bed assignment: Hungarian algorithm
BedAssigner gathers scheduled patients without beds and builds a patient-by-bed cost matrix. ICU mismatch and conflicts with another bed reservation interval are forbidden edges. Costs among feasible beds are:
- priority level * 100 (Emergency 100, Urgent 200, Elective 300);
- minus waiting minutes;

- +1,000 if a non-ICU patient uses an ICU bed;
- clamped to zero minimum.
HungarianAlgorithm uses a potentials-based O(n^3) assignment implementation with rectangular matrices, positive-infinity forbidden edges, and unmatched rows. Beds are reserved from actual surgery start until 24 hours after surgery completion. If no bed fits, the OR slot, staff slot, and scheduled state are rolled back. The assignment cost is hand-designed, not clinically calibrated.

4.6 Emergency path
Choice 4 validates nonempty name, surgery enum, positive duration, true/false ICU value, and strict 24-hour HH:mm arrival time before adding an emergency patient. It preserves already-started procedures and their resources, releases future OR/staff/bed reservations, and replans pending cases.

4.7 Manual patient discharge
Choice 8 asks for a patient ID and discharge time in HH:mm format. The patient must be scheduled and have an assigned bed; discharge cannot be earlier than the scheduled surgery completion. The system releases the assigned bed, records discharged state/time, and keeps the OR slot as history. Discharged patients remain counted as scheduled in KPIs and are excluded from later scheduling pipeline runs. Patient listing shows the discharge time.

4.8 KMP search
Choice 7 searches every patient and staff name. KMP computes the pattern's LPS (longest proper prefix that is also suffix) array, then scans without backing up the text pointer. Inputs are lowercased for case-insensitive search. Per name, time is O(n+m), preprocessing O(m). Empty pattern returns true and matches all records; empty text with nonempty pattern returns false.

5. COURSE OUTCOME (CO) MAPPING
======================================================================

This maps algorithms in the current source to the six handout COs; it does not claim the full syllabus was implemented.

CO1: Select a strategy for a problem class.
Shown by choosing min-cost flow for capacity-constrained routing, LPT approximation for OR workload, subset DP for OR timing, Hungarian assignment for beds, and KMP for substring search. CO1 is the rationale connecting the pipeline.

CO2: Linear-time string algorithms / suffix structures.
Implemented: KMP name search, O(n+m) per record. Not implemented: Z, Rabin-Karp, Aho-Corasick, suffix arrays/LCP, suffix automaton.

CO3: Advanced DP patterns.
Implemented: subset DP sequences unique patients for one OR with existing reservations, surgeon availability, priority, and waiting cost. Not implemented: tree/SOS DP, matrix-chain, or sequence alignment.

CO4: Network flow and max-flow/min-cut.
Implemented: min-cost maximum flow routes each patient to at most one compatible hospital within separate ICU/General capacities, minimizing preferred-hospital and distance costs among maximum flows. No min cut is computed or reported. Hungarian bed assignment is separate from flow.

CO5: NP-hardness and approximation.
Implemented: LPT load-balancing heuristic, greedily assigning to the least-loaded compatible OR. No NP-completeness reductions or approximation ratio calculation is implemented. Do not claim a proved ratio for the full hospital problem.

CO6: Randomized and parallel algorithms.
Implemented: random-pivot quicksort before LPT. Output sort is correct while runtime is probabilistic (expected O(n log n), worst O(n^2)); this is Las Vegas-style randomization. No parallel primitives, Miller-Rabin, or randomized hashing is implemented.

Hungarian/Kuhn-Munkres is cross-cutting for assignment and most naturally relates to CO4's capacity/assignment theme, but should be named separately from max flow.

6. HOW TO INTERPRET OUTPUT
======================================================================

Pipeline lines identify the routing, load balancing, OR scheduling, and bed assignment stages. "Hospital received N patients" is the max-flow route count, not the number that ultimately receive an OR slot. A warning means an OR could not support that surgery.

KPIs:
- Processing Rate counts Patient.isScheduled flags / total patients and integer percentage.
- Average waiting time is integer average among scheduled flags.
- Makespan is latest scheduled start plus surgery duration.
- Bed Reservations is reserved beds / inventory; it is a plan reservation ratio, not a real-time census.
- OR utilization sums each operation overlap with the fixed 720-minute 08:00-20:00 reporting window, then divides by 720 and caps the result at 100%.

Schedule view prints OR slots, patient ID/name, priority, and the assigned surgeon. It omits bed IDs, individual unscheduled reasons, violation reports, and an optimal baseline.

9. PPT SCOPE VS IMPLEMENTATION
======================================================================

Implemented: menu and fixed dataset; min-cost max-flow with preference/distance and bed-type capacities; LPT OR balancing; surgeon-aware subset DP; interval-aware Hungarian bed assignment; emergency replanning; manual discharge; strict intake validation; KMP; randomized quicksort; KPI and schedule reports.

- Qualified surgeon specialization, shift, and assignment conflicts are enforced; anesthetist/nurse staffing is not modeled.

- Waiting is included in the local schedule score; makespan and OR utilization are reported, but there is no joint global optimization across all hospitals/ORs.
- No constraint-violation report is generated.
- Emergency replanning preserves started procedures and rebuilds future cases; it remains a single-day simulation without date-aware admissions.
- Real-time data, prediction, ML, charts, monitoring, adaptive optimization are future-scope only.
- Handout algorithms such as Z, Rabin-Karp, suffix structures, bitmask DP for TSP/set cover, tree/SOS DP, Miller-Rabin, and parallel primitives are not implemented.

13. ENHANCEMENT IMPLEMENTATION UPDATE
======================================================================

This section records how the current source implements the enhancements and provides reproducible verification details. The current source includes the
following changes:

1. Schedule consistency: OR slots, patient scheduled flags, assigned surgeons,
   and bed assignments are committed/removed together. A scheduled patient must
   have a feasible OR, qualified surgeon, and bed reservation. Unassignable
   patients are reset rather than counted as scheduled.
2. Routing preference: min-cost max-flow first maximizes routed patient count,
   then minimizes cost. A preferred-hospital mismatch has a strong penalty;
   among otherwise equal choices, Haversine distance from patient coordinates
   favors a nearer hospital. Patients default to the sample service-area
   center; setLocation(latitude, longitude) allows a real origin.
3. Explicit ICU capacity: hospital flow nodes have separate General and ICU
   lanes with capacities equal to the respective available bed counts. ICU
   patients can only use ICU lanes; non-ICU patients prefer General beds and
   may use ICU capacity if required to preserve maximum flow.
4. Bed/OR coupling: Hungarian assignment treats ICU mismatch and overlapping
   bed reservation intervals as forbidden edges. If no bed fits the full
   interval, the OR slot, surgeon slot, and patient schedule state are rolled
   back together.
5. Time scheduling: subset DP sequences individual patients, shifts their
   start after existing OR slots and surgeon conflicts, and weighs priority
   against waiting cost. It is exact for at most 14 patients assigned to one OR;
   larger lists use a fixed-candidate weighted-interval fallback.
6. Assignment robustness: Hungarian supports rectangular matrices, positive
   infinity forbidden edges, and explicit unmatched rows. Regression cases
   cover known square optimum, rows>columns, and forbidden assignments.
7. Bed reservation interval: bed reservation starts at the actual scheduled
   surgery start and ends 24 hours after surgery completion. Manual discharge
   releases it sooner. The displayed bed percentage is named "Bed Reservations"
   and counts beds currently reserved in the plan, not a real-time census.
8. Emergency replanning: already-started procedures and their OR, staff, and
   bed records stay in place. Future procedures are removed from all three
   resource records and reconsidered with the emergency case.
9. Input validation: emergency name, surgery enum, positive duration, strict
   HH:mm time, and true/false ICU input are validated before patient insertion.
10. Staff feasibility: a surgeon with matching specialization and a compatible
    shift must be available for every operation. The schedule output prints
    surgeon names. Sample staff specializations were adjusted to cover the
    configured OR types; anesthetist/nurse staffing is not modeled.
11. Regression suite: tests/RegressionTests.java is a dependency-free repeatable
    suite for max-flow cost, routing preference/distance, ICU capacity,
    Hungarian, KMP, randomized sort/LPT, DP with existing slots and surgeon
    availability, utilization clipping, bed intervals, pipeline invariants,
    input validation, and emergency preservation.
12. OR utilization clips each stored operation to the configured reporting
    window and caps the ratio at 100 percent.

14. PERSISTENCE LAYER AND REST APPLICATION UPDATE
======================================================================

The Spring REST application now stores operational state in a local, file-backed H2 database. This is a persistence layer for the project simulation; it does not make the application a live hospital system. The console workflow described in Sections 4 and 7 remains an in-memory workflow.

Persistence design
- JPA entities represent hospitals, operating rooms, beds, staff, patients, schedules, bed reservations, and discharge records. Enumerated schedule and reservation states retain lifecycle and history.
- Spring Data repositories provide database access. DomainModelMapper reconstructs the existing plain Java models, including active reservations and schedule history, so the routing and scheduling algorithms remain independent of JPA.
- DemoDataInitializer loads the existing sample dataset only when the database has no hospital and patient records. Restarting the service does not reseed or overwrite an existing dataset.
- SchedulerService coordinates REST actions in transactions. A schedule run validates and persists the resulting schedule and active bed reservations, while prior schedule records are retained as superseded history. Emergency replanning updates future cases while preserving procedures already in progress. Discharge releases a reservation and writes a durable discharge record.
- The service validates feasible OR, qualified surgeon, bed type, and reservation interval before saving assignments. Database transaction rollback is intended to prevent partially saved scheduling updates if an operation fails.

Database configuration and API
The default JDBC URL uses H2 in file mode at ./data/hospital_scheduler with AUTO_SERVER enabled. The schema is updated on application startup. H2 console access is enabled at /h2-console for local development. The data directory is ignored by Git. The REST API retains the existing hospital, patient, scheduling, emergency, and discharge workflows and provides patient creation plus schedule and discharge history reads. Schedule records include their status, algorithm path, and timestamps.

An emergency patient was then created and scheduled; discharge was recorded, and a further restart retained the 13 patients, 13 schedule records (12 active and one completed), and one discharge record.
